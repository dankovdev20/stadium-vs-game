# Задачи и заметки для бэкенда (обновлено 2026-09-20)

## Открытые задачи

- **[НУЖНО] Один сокет может занять ОБЕ роли в лобби.**
  `GameRoom.handleSelectRole` (`server/src/gameRoom.js:79-108`) проверяет
  только занятость запрошенного слота (`this.players[requestedRole]`), но не
  проверяет, есть ли у самого `socket` уже назначенная роль. Из-за этого один
  и тот же клиент/сокет может сначала вызвать `player:select_role('player_1')`,
  а затем `player:select_role('player_2')` — оба слота помечаются занятыми
  (`isConnected: true`), и комната сама переходит в `CUSTOMIZATION`/игру без
  реального второго игрока. На стенде для двух детей это критично: один
  игрок может случайно "занять" обе стороны с одного экрана.

  Со стороны фронтенда я это уже закрыл (`screens/LobbyScreen/LobbyScreen.tsx`) —
  кнопка второй роли блокируется локально сразу по тапу, ещё до ответа
  сервера. Но это UI-подстраховка, а не настоящая защита: сервер как источник
  истины всё ещё примет второй `player:select_role` от того же `socket.id`,
  если запрос придёт в обход обычного клиента (или до того, как фронт
  успел отрисовать блокировку).

  **Предлагаемый фикс** — в начале `handleSelectRole`, до проверки занятости
  слота, добавить проверку `if (socket.role) { ...emit ROLE_TAKEN или новый
  код ошибки...; return; }`, то есть один `socket` может выбрать роль только
  один раз за жизнь соединения (до дисконнекта/hard reset). Отдельно стоит
  решить, что делать, если это тот же сокет повторно жмёт СВОЮ уже занятую
  роль (сейчас по факту это тоже проходит и просто перезаписывает те же
  данные) — наверное, безопасно тоже ранний `return`, раз фронт всё равно
  теперь не даёт повторно тапнуть.

Это живой файл-стыковка между фронтендом и бэкендом. Я (фронтенд-агент)
больше не редактирую `server/` напрямую — всё, что нужно от бэка, попадает
сюда, а не молча в код, чтобы не сбивать с толку того, кто ведёт эту папку.

## Что уже добавлено в `server/` за последние заходы (для контекста)

Все изменения — чистые ДОБАВЛЕНИЯ, ни одна существующая строка логики не
удалена (проверяемо: `git diff HEAD -- server/`). Единственная изменённая
(не добавленная) строка — комментарий над `game:restart` в `server.js`,
потому что поведение реально перестало быть мгновенным рестартом. Полное
описание контракта — `shared/put_me_in_context.md`, РАЗДЕЛ 7.

1. **Голосование "Играть снова"** (`GameRoom.handleRestartGame`, `_doRestart`,
   `finishGame`) — раньше один клик рестартовал матч для обоих сразу; теперь
   ждём подтверждения ОБОИХ 10 секунд (`RESTART_VOTE_TIMEOUT_MS`), иначе
   `handleForceReset()` уводит комнату в LOBBY. Причина — выставочный формат:
   нельзя, чтобы один ребёнок перезапускал матч за ушедшего партнёра.
2. **Автосброс при простое** (`armIdleTimer`, `IDLE_TIMEOUT_MS` = 90 сек) —
   если комната застряла в LOBBY/CUSTOMIZATION без действий, сама сбрасывается.
   Специально НЕ действует во время PLAYING/ROUND_RESULT/GAME_OVER.
3. **`state:sync.characters`** — раньше `character:submit` сохранялся
   (`player.character`), но никогда не рассылался обратно клиентам. Теперь
   `broadcastState()` включает `{ player_1, player_2 }` с последним
   отправленным `{headId,bodyId,legsId}` каждого (или `null`).
4. **`state:sync` теперь рассылается сразу после ОДНОГО выбора зоны**
   (`handleMakeChoice`), не только когда выбрали оба. Иначе `choicesStatus`
   не обновлялся до конца раунда, и клиент не мог понять "мой выбор принят"
   (кнопка не блокировалась, повторный тап тем же игроком тихо отклонялся
   защитой от спама). **Важно**: клиент с этого захода больше не зависит от
   этого строго — на клиенте теперь свой синхронный замок выбора
   (`screens/GameScreen/model/useGameScreenModel.ts`), а `choicesStatus`
   используется только как подстраховка при реконнекте. Если этот
   дополнительный `broadcastState()` мешает (например, планируется троттлинг
   рассылок) — можно убрать без последствий для текущего фронтенда.

Тесты на всё это — `server/tests/gameRoom.test.js` (9/9 зелёных, `npm test`).

- **[РЕШЕНО // РЕАЛИЗОВАНО 2026-09-20] Переассоциация роли при реконнекте (sessionToken).**
  В `GameRoom.handleSelectRole` теперь генерируется криптографический `sessionToken`
  (`crypto.randomUUID()`), который возвращается в `role:assigned`:
  `{ role, sessionToken }`.
  Добавлен слушатель `player:reconnect` (`GameRoom.handleReconnect`):
  клиент отправляет `{ sessionToken, role? }`.
  Сервер сверяет токен, восстанавливает `socket.role`, обновляет `socketId`,
  ставит `isConnected = true`, отменяет таймер сброса комнаты (`disconnectTimer`)
  и эмитит `role:assigned` (`reconnected: true`) + `room:player_reconnected` + `state:sync`.
  Все 12 тестов зелёные (`server/tests/gameRoom.test.js`).
- Новых полей контракта для единой сцены матча (см. фронтенд-changes ниже)
  не потребовалось — всё выводится на клиенте из уже существующих
  `strikerRole`/`keeperRole`/`myRole`/`characters`.

## Что изменилось на фронтенде (просто для контекста, не требует от тебя действий)

`screens/GameScreen/` полностью переехал на единую сцену матча (одна камера,
роли визуально меняются местами, стрелочка над своим персонажем) вместо
раздельных "видов" нападающего/вратаря — по референсу анимаций, который
прислал Даниил. Конструктор персонажа (`feature/character-builder/`)
перекладён под фикс 1920×1080 без скролла. Ничего из этого не трогает
контракт WebSocket.
